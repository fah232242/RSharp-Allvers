# R# Advanced Guide

This guide documents the implemented R# compiler and tooling in the repository. It is intended for
developers building larger programs, libraries, packages, games, or tooling around R#.

R# currently follows a compact architecture:

```text
.rsharp source
    ↓
lexer
    ↓
parser / AST
    ↓
module loader
    ↓
name resolution + type checking
    ↓
C11 code generation
    ↓
gcc / clang
    ↓
native executable
```

The repository's CLI currently reports version `1.2.0`; the archive directory is named
`rsharp-lang2.0.0`. Treat the compiler implementation and tests as authoritative when they differ from
older prose.

---

# 1. Compiler architecture

The Python implementation is organized roughly as:

```text
rsharp/
├── cli.py
├── driver.py
├── pkg.py
├── compiler/
│   ├── ast.py
│   ├── checker.py
│   ├── codegen.py
│   ├── errors.py
│   ├── lexer.py
│   ├── loader.py
│   ├── natives.py
│   └── parser.py
├── packages/
│   ├── algo/
│   ├── stats/
│   ├── text/
│   └── vec/
└── runtime/
    └── rt.h
```

The driver loads source, invokes the loader/parser, type-checks the resulting AST, generates C, and
invokes the host C compiler.

The normal build command uses approximately:

```text
$CC -O2 -std=gnu11 -w -o output generated.c -lm
```

where `CC` defaults to `gcc`.

The REPL uses a similar C compilation path with `-O1`.

---

# 2. Lexical and syntactic model

R# uses:

- identifiers matching `[A-Za-z_][A-Za-z0-9_]*`;
- decimal integers;
- hexadecimal integers;
- integer underscore separators;
- floating-point literals;
- double-quoted strings;
- interpolated `$"..."` strings;
- `//`, `#`, and block comments;
- semicolon-terminated simple statements;
- brace-delimited blocks.

Integer literals support forms such as:

```rsharp
let a = 1_000_000;
let b = 0xFF;
```

Floating-point literals include:

```rsharp
let x = 1.5;
let y = 2e3;
```

String escapes are:

```text
\n \t \r \\ \" \0
```

---

# 3. Program execution model

An R# source file may contain:

- imports;
- struct declarations;
- function declarations;
- constants;
- top-level statements.

Top-level script statements execute in source order. If a `main()` function exists, it is called after
the script has run.

`main` must have:

```rsharp
fn main() {
    ...
}
```

It cannot accept parameters or return a value.

Function declarations are registered before function bodies are checked, so a function can call a
function declared later:

```rsharp
print(later(5));

fn later(x: int) -> int => x + 1;
```

Functions cannot see ordinary top-level `let`/`mut` variables through lexical capture. Top-level
mutable state is handled as compiler-generated globals and is visible where the implementation permits
it. Top-level `const` declarations are available to later functions.

There are no closures.

---

# 4. Static type system

The implemented scalar types are:

```text
int
float64
bool
string
void
```

`int` is a signed 64-bit integer and `int64` is accepted as an alias.

Composite types are:

```text
T[]
map<T>
StructName
```

Examples:

```rsharp
int[]
string[][]
map<int>
map<string[]>
Point
```

The compiler represents arrays and maps internally as tagged type tuples. Struct types are identified
by name.

Unsupported type concepts include:

```text
int8, int16, int32
uint8, uint16, uint32, uint64
float32
char
byte
any
never
T?
```

They should not be documented or used as implemented language features.

---

# 5. No implicit numeric conversion

R# deliberately rejects:

```rsharp
let x = 1 + 2.0;
```

Use:

```rsharp
let x = float64(1) + 2.0;
```

This rule is important for library authors because function arguments are also checked exactly.

For example:

```rsharp
fn area(radius: float64) -> float64 {
    return 3.14159 * radius * radius;
}

// area(5);          // type error
area(float64(5));    // valid
```

---

# 6. Operators and precedence

The implemented precedence, from low to high, is approximately:

```text
||
&&
==
!=
< <= > >= in not in
+ -
* / %
unary - !
postfix call/index/member
**
```

Exponentiation is parsed as a special postfix/unary-level operator and supports:

```rsharp
2 ** 10
2.0 ** 0.5
```

Boolean operations short-circuit.

Evaluation order is explicitly left-to-right. This matters when expressions contain calls with side
effects:

```rsharp
print(f(), g());
```

`f()` executes before `g()`.

This differs from relying on C argument-evaluation behavior and is preserved by the R# code generator.

---

# 7. Integer semantics

Integer arithmetic uses checked operations.

The runtime panics for:

- integer overflow;
- division by zero;
- invalid integer operations such as invalid bounds/operations generated by runtime helpers.

Integer `/` truncates toward zero.

There is no Python-style `//` operator because `//` begins a comment.

Modulo is available through `%`.

---

# 8. Floating-point semantics

`float64` follows the host C/IEEE floating-point behavior.

Examples:

```rsharp
let x = 1.0 / 0.0;
print(x);
```

Floating-point infinity can also be accessed through:

```rsharp
math.inf
```

Unlike integers, floating-point operations are not treated as checked integer operations.

---

# 9. Arrays: reference semantics

Arrays are heap-backed runtime objects.

The important semantic distinction is:

```text
struct values → copied
arrays → aliased/referenced
```

Example:

```rsharp
mut a = [1, 2];
mut b = a;

b[0] = 99;

print(a); // [99, 2]
```

This makes arrays suitable for mutable collections, but library authors must understand aliasing.

### Mutation checks

The checker tracks mutability of the root expression. Operations such as:

```rsharp
xs.push(x);
xs.pop();
xs.reverse();
xs.sort();
xs.extend(other);
xs.clear();
xs[i] = value;
```

require the appropriate mutable root.

This prevents:

```rsharp
let xs = [1, 2];
// xs.push(3);       // compile error
```

while allowing:

```rsharp
mut xs = [1, 2];
xs.push(3);
```

Array element types are homogeneous.

Nested arrays are valid:

```rsharp
mut grid = [[1, 2], [3, 4]];
grid[1][0] = 30;
```

# 10. Array operations

Implemented methods:

```text
push(T) -> void
append(T) -> void
pop() -> T
contains(T) -> bool
reverse() -> void
sort() -> void
extend(T[]) -> void
clear() -> void
copy() -> T[]
```

`contains` is currently restricted to arrays whose element type is a scalar supported by the checker.

`sort` supports:

```text
int[]
float64[]
string[]
```

and rejects other element types.

Array slicing returns another array object containing the selected range.

---

# 11. Maps: implementation constraints

Maps are declared:

```rsharp
map<T>
```

Keys are always strings.

```rsharp
mut scores: map<int> = {
    "alice": 10,
    "bob": 20
};
```

The current runtime uses an insertion-ordered representation with linear lookup.

This means a map is semantically convenient but should not be assumed to provide hash-table-level
constant-time lookup.

Methods:

```text
get(key: string, default: T) -> T
keys() -> string[]
values() -> T[]
remove(key: string) -> void
clear() -> void
```

Membership uses:

```rsharp
if "alice" in scores {
    ...
}
```

Map mutation requires a mutable root.

Maps can contain structs:

```rsharp
mut players: map<Player> = {};
players["alice"] = Player { ... };
players["alice"].hp -= 10;
```

---

# 12. Strings are byte-oriented

The runtime treats strings as byte sequences.

Consequences:

```rsharp
"hello".length
```

is straightforward, but:

```rsharp
"héllo".length
```

counts UTF-8 bytes, not Unicode code points.

Indexing is therefore ASCII-oriented.

For Unicode-heavy applications, do not assume Python-like Unicode string semantics.

---

# 13. String methods

The checker implements:

```text
upper() -> string
lower() -> string
strip() -> string
contains(string) -> bool
startswith(string) -> bool
endswith(string) -> bool
replace(string, string) -> string
split(string) -> string[]
find(string) -> int
join(string[]) -> string
```

`join` is invoked on the separator:

```rsharp
let result = ", ".join(["a", "b", "c"]);
```

The checker recognizes:

```text

sum
sorted
```

Important type behavior:

### `len`

Accepts:

```text
string
```

### `range`

Accepts one to three `int` arguments and returns `int[]`.

```rsharp
range(5)
```

Accept either:


### `read_file` / `write_file`

These operate on text files:

### `assert`

```rsharp

```

# 15. Struct representation and semantics

Structs are value types:

```rsharp
struct Point {
    x: float64,
    y: float64
}
```

The checker registers structs before checking functions, but a struct type used as a field must already
be declared. Recursive structs are not supported.

For example:

```rsharp
struct Vec {
    x: float64,
    y: float64
}

struct Player {
    position: Vec,
    hp: int
}
```

is valid.

A struct with a field referring to itself is not.

Struct literals require all fields exactly once:

```rsharp
let p = Point {
    x: 1.0,
    y: 2.0
};
```

Unknown, duplicate, or missing fields are compile errors.

Struct equality is not implemented, so:

```rsharp
// p1 == p2
```

is rejected.

Struct methods/`impl` are not implemented.

# 16. Modules and loader resolution

Imports are resolved by the module loader.

Supported forms include:

```rsharp
import math;
import local;
import local as l;

from local import add;
from local import add as plus;

import thing from "@rsharp/thing";
```

The repository's loader checks native modules:

```text
math
random
time
game
```

and local/vendored/bundled paths.

Local resolution includes forms such as:

```text
./m.rsharp
./m/lib.rsharp
rsharp_packages/m/lib.rsharp
```

The loader searches parent directories for vendored packages.

Circular imports are detected and rejected.

Modules may contain only:

- functions;
- structs;
- constants;
- imports.

Ordinary top-level executable statements are not allowed inside modules.

# 17. Native module architecture

Native modules are described in:

```text
rsharp/compiler/natives.py
```

and implemented through the generated C runtime.

The native function table contains signatures plus C expressions. For example, the game module maps
R# functions to runtime functions such as:

```text
rs_game_delta()
rs_game_fixed_delta()
rs_game_frame()
rs_game_quit()
rs_fb_window()
rs_fb_clear()
rs_fb_pixel()
rs_fb_rect()
rs_fb_circle()
rs_fb_line()
rs_fb_get()
rs_fb_save()
```

This is the current native-extension mechanism. There is no general user-facing FFI.

# 19. `random`

The native random module exposes:

```text
random() -> float64
randint(int, int) -> int
seed(int) -> void
```

Example:

```rsharp
import random;

random.seed(12345);

for i in 0..5 {
    print(random.randint(1, 6));

```

Because the REPL replays history, random calls are specifically discouraged there.

# 20. `time`

The module exposes:

```text
now() -> float64
sleep(num) -> void
```

where `num` accepts an integer or float.

`time.now()` is wall-clock time. `sleep` is a blocking operation.

The REPL documentation warns against time-dependent expressions because entries are replayed.

# 22. Package/project manifests

Projects use:

```text
rsharp.toml
```

A basic manifest looks like:

```toml
[package]
name = "my_app"
version = "0.1.0"
description = "My R# application"
license = "MIT"

[dependencies]
```

Dependencies can be added with:

```sh
rsharp pkg add @rsharp/text
```

The package manager vendors package files into:

```text
rsharp_packages/
```

and records dependency information in:

```text
rsharp.lock
```

The lock file contains package names, versions, sources, and SHA-256 directory checksums.

# 25. Testing architecture

Tests are ordinary `.rsharp` files.

The CLI recursively scans the requested test directory for `.rsharp` files, ignoring files beginning
with `_`.

A runtime test contains:

```rsharp
print(add(2, 3)); // expect: 5
```

The runner compares stdout lines exactly.

A compile-error test contains:

```rsharp
// expect-error: cannot assign
```

The runner compiles the source and checks that the reported error contains the expected text.

This is useful for language development because type-system regressions can be tested alongside normal
program output.

---

# 26. Error reporting

Compiler errors are represented by `RSharpError` and are reported with source location information.

The normal CLI format is conceptually:

```text
file:line:col: error: message
    source line
    ^
```

Runtime panics are printed as:

```text
panic: ...
```

and the language specification documents exit code `101` for runtime panics.

CLI-level/internal failures use other exit statuses.

# 27. Game runtime

The game runtime is intentionally headless.

A program becomes a game with:

```rsharp
import game;

game "My Game";
```

The declaration is only legal in the main program.

At least one of these hooks is required:

```text
update(delta: float64)
draw()
```

Optional hooks:

```text
start()
fixed_update(delta: float64)
shutdown()
```

Invalid signatures are compile errors.

---

# 28. Game lifecycle

The conceptual loop is:

```text
start()
    ↓
fixed_update(delta) as fixed simulation requires
    ↓
update(delta)
    ↓
draw()
    ↓
repeat
    ↓
shutdown()
```

The implementation tracks fixed and frame timing internally.

Games terminate when:

```rsharp
game.quit();
```

is called or the configured maximum frame count is reached.

Use:

```rsharp
game.max_frames(120);
```

for deterministic finite runs.

---

# 29. Deterministic game timing

By default the game loop uses simulated time:

```text
delta = 1 / target_fps
```

and does not sleep to synchronize with wall-clock time.

This makes headless tests reproducible.

To use wall-clock timing:

```rsharp
game.realtime(true);
```

The runtime can then sleep to maintain the target frame rate.

Set the target with:

```rsharp
game.target_fps(60);
```

Timing queries:

```text
game.delta()
game.fixed_delta()
game.frame()
game.seconds()
game.fps()
```

---

# 30. Software framebuffer

Create a framebuffer with:

```rsharp
game.window(320, 180);
```

Despite the name, this does not create an OS window. It establishes the framebuffer dimensions.

Query:

```rsharp
game.width()
game.height()
```

Clear:

```rsharp
game.clear(0, 0, 0);
```

Draw:

```rsharp
game.pixel(x, y, r, g, b);
game.fill_rect(x, y, w, h, r, g, b);
game.circle(cx, cy, radius, r, g, b);
game.line(x0, y0, x1, y1, r, g, b);
```

Colors are integer RGB components from `0` to `255`.

Drawing is clipped.

Read a pixel:

```rsharp
let color = game.pixel_at(x, y);
```

The result is encoded as:

```text
0xRRGGBB
```

Save the framebuffer:

```rsharp
game.save_frame("frame.ppm");
```

The output is a PPM image.

Drawing before `game.window()` causes a runtime panic with a clear diagnostic.

# 31. Example headless game

```rsharp
import game;
import vec;

game "Bounce";

struct Ball {
    pos: Vec2,
    vel: Vec2,
    radius: int
}

mut ball = Ball {
    pos: vec.vec2(40.0, 20.0),
    vel: vec.vec2(70.0, 0.0),
    radius: 6
};

fn start() {
    game.window(160, 90);
    game.max_frames(240);
}

fn fixed_update(dt: float64) {
    ball.vel.y += 500.0 * dt;
    ball.pos = vec.add2(ball.pos, vec.scale2(ball.vel, dt));

    if ball.pos.y > 82.0 {
        ball.pos.y = 82.0;
        ball.vel.y = -ball.vel.y * 0.85;
    }

    if ball.pos.x > 154.0 or ball.pos.x < 6.0 {
        ball.vel.x = -ball.vel.x;
    }
}

fn update(dt: float64) {
}

fn draw() {
    game.clear(15, 20, 35);
    game.circle(
        int(ball.pos.x),
        int(ball.pos.y),
        ball.radius,
        250, 190, 50
    );
}

fn shutdown() {
    game.save_frame("bounce_last_frame.ppm");
}
```

The repository includes a similar `examples/bounce/main.rsharp`.

# 32. Game runtime limitations

The current runtime does **not** provide:

- native windows;
- keyboard/mouse/gamepad input;
- GPU rendering;
- OpenGL/Vulkan/DirectX;
- shaders;
- audio;
- 3D rendering;
- ECS;
- physics;
- scenes/prefabs;
- animation;
- UI;
- networking;
- asset loading/pipeline;
- hot reload;
- editor;
- profiler;
- debugger.

The software framebuffer is therefore best treated as a deterministic rendering/testing substrate rather
than a production game engine.

# 34. Performance model

R# is compiled to C and then native code, so the generated program is not an interpreter.

The normal compiler invokes the C compiler with `-O2`.

However, language/runtime design still affects performance:

- arrays are heap-backed;
- map lookup is linear;
- strings are runtime-managed;
- there is no garbage collector;
- allocations are reclaimed at process exit rather than through a full GC;
- slices/copies and array operations can allocate;
- high-level collection operations should not be assumed allocation-free.

The absence of a GC is acceptable for short tools and deterministic simulations but is a significant
limitation for long-lived applications.

---

# 35. Memory model and safety boundary

R# does not expose:

```text
pointers
references
unsafe blocks
manual free
malloc/free
FFI
```

There is no ownership or borrow checker.

This means the language is simpler than Rust/C++, but it also lacks their explicit lifetime/aliasing
systems.

The generated C runtime owns the implementation details of arrays, strings, maps, and game buffers.

---

# 36. REPL internals and limitations

The REPL is intentionally simple.

For every entry it:

1. appends the entry to accepted history;
2. recompiles the complete history;
3. builds a temporary executable;
4. runs it;
5. prints only newly observed output.

This explains why side-effecting operations are discouraged:

```text
input()
random.*
time.*
```

A previous entry can be executed again when the next entry is evaluated.

The REPL recognizes expressions and may turn a bare expression into a temporary `print(...)` attempt.

It also tracks bracket depth so multi-line blocks can be entered interactively.

---

# 37. Native extension points

The current extension path for standard/native modules is internal.

`rsharp/compiler/natives.py` declares signatures and maps them to generated C expressions.

For example:

```python
"sqrt": (["num"], "float64", "sqrt({0})")
```

The type checker understands `num` as either `int` or `float64`.

A native module therefore needs:

1. a compiler-side signature entry;
2. a generated C expression/function mapping;
3. runtime support in the C runtime where necessary.

This is not the same as a public FFI. User programs cannot currently declare arbitrary C bindings.

---

# 38. C backend constraints

The backend generates GNU C11, not strict ISO C11.

The driver invokes:

```text
-std=gnu11
```

and the implementation uses GNU extensions, including statement expressions in generated code.

The C compiler is therefore part of the effective target environment.

`CC` can select another compatible compiler:

```sh
CC=clang rsharp build src/main.rsharp -o app
```

---

# 39. Generated C inspection

For backend debugging:

```sh
rsharp emit-c program.rsharp > program.c
```

Then inspect or compile the generated C yourself.

This is useful for:

- understanding runtime representation;
- diagnosing compiler backend problems;
- benchmarking generated code;
- investigating C compiler diagnostics.

# 41. Designing libraries that work well in today's R#

Because there are no generics or first-class functions, design APIs around concrete types and explicit
functions.

Prefer:

```rsharp
fn sum_ints(xs: int[]) -> int {
    return sum(xs);
}
```

over an imagined generic:

```text
fn sum<T>(...)
```

Do not design callback-based APIs because closures/function values do not exist.

Prefer explicit lifecycle functions:

```text
init
update
process
shutdown
```

rather than callback registration.

For mutable data, decide explicitly whether a function should:

- mutate an array;
- return a new array;
- mutate a struct through a mutable root;
- return a modified struct value.

This matters because arrays and structs have different semantics.

# 42. Testing libraries

A package should include R# tests that verify:

- normal output;
- compile errors;
- boundary cases;
- mutability rules;
- empty arrays/maps;
- indexing;
- package imports.

For example:

```rsharp
from mylib import clamp;

print(clamp(5, 0, 10));   // expect: 5
print(clamp(-2, 0, 10));  // expect: 0
print(clamp(20, 0, 10));  // expect: 10
```

Compile-time API misuse should be covered with `expect-error` tests.

# 44. Advanced example: algorithm + package + struct

```rsharp
import math;
from algo import is_prime;
from vec import Vec2, vec2, len2;

struct Particle {
    position: Vec2,
    speed: float64,
    id: int
}

fn distance_from_origin(p: Particle) -> float64 {
    return len2(p.position);
}

fn main() {
    mut particles: Particle[] = [];

    for i in 0..20 {
        if is_prime(i) {
            particles.push(Particle {
                position: vec2(float64(i), float64(i * 2)),
                speed: math.sqrt(float64(i)),
                id: i
            });
        }
    }

    for p in particles {
        print(
            $"particle {p.id}: distance={distance_from_origin(p)}, speed={p.speed}"
        );
    }
}
```

This style is close to the current language's sweet spot: typed functions, value structs, arrays,
modules, and concrete packages.

# 45. What R# is good at today

The current implementation is a reasonable fit for:

- teaching compiler concepts;
- small command-line programs;
- deterministic algorithm experiments;
- typed scripting;
- native utilities;
- small data-processing tools;
- package/library experiments;
- headless rendering tests;
- deterministic game prototypes.

It is not yet a replacement for:

- C/C++ systems programming;
- Rust-style ownership-heavy systems work;
- Python's ecosystem;
- production GUI applications;
- network servers;
- full game engines;
- GPU programming.

# 46. Repository development workflow

When modifying R# itself, a useful workflow is:

```sh
# run the existing tests
PYTHONPATH=. python3 -m rsharp test tests

# check a program
PYTHONPATH=. python3 -m rsharp check examples/primes.rsharp

# inspect generated C
PYTHONPATH=. python3 -m rsharp emit-c examples/primes.rsharp

# build a native binary
PYTHONPATH=. python3 -m rsharp build examples/primes.rsharp -o primes
```

After changing the parser or checker, add both:

1. a positive test proving the new syntax/behavior;
2. a negative test proving invalid programs remain rejected.

For backend changes, inspect generated C and run the complete test suite.

# 48. Future-facing design guidance

If R# is extended toward a larger systems/programming language, the most impactful additions would be:

1. first-class function values and closures;
2. a real memory-management strategy;
3. a public FFI;
4. richer collections and generics;
5. stronger module/package versioning;
6. formatter/linter/LSP;
7. debugger and profiler;
8. LLVM/WASM or additional native backends;
9. real window/input/audio support for games;
10. ECS/physics/assets only after the lower-level runtime interfaces are stable.

The existing architecture is small enough that these should be added incrementally with compiler tests
for every language rule.

# 49. Final mental model

For advanced users, the most important current R# rules are:

```text
R# is statically typed.
R# does not implicitly convert numbers.
R# uses semicolons and braces.
R# has Python-style conveniences, not Python semantics.
Arrays are reference-like.
Structs are value types.
Maps use string keys.
Functions are not first-class.
There is no GC.
There is no FFI.
The native target is generated GNU C11.
The package manager is offline.
The game runtime is headless/software-rendered.
```

Build programs around those guarantees and the current implementation is predictable and useful.
